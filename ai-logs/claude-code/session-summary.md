# Claude Code session summary

Chronological summary of one Claude Code session. Prompts are quoted as typed (typos kept). The API token has been removed.

## 1. Bootstrap (day before the slot)

**Prompt:** a long setup spec: Expo + TypeScript strict + Expo Router, react-native-web, TanStack Query, a typed API client reading the base URL **and token** from `EXPO_PUBLIC_*` env variables, ESLint/Prettier/Jest, a mobile-first max-width layout, a static export, SPA fallback config, `ai-logs/`, and git with small commits.

**What the AI did:**
- Scaffolded Expo SDK 58 (`create-expo-app`, blank TypeScript template).
- Added Expo Router, set web output to a single-page app, added a `Screen` max-width container, and a fetch client + QueryClient.
- Set up lint, Prettier and Jest, with one client test.
- Chose Vercel (`vercel.json` + `public/_redirects` for Netlify).
- Checked the result: started the dev server, built for production, took 390px screenshots in headless Chrome, and made 4 commits.

**Checked / corrected along the way:**
- Port 8081 was used by another local project, so the dev server ran on a different port instead of stopping that project.
- Jest crashed because the local Watchman install was broken; Watchman was turned off for Jest.
- The first "phone" screenshot looked clipped on the right. The AI traced this to headless Chrome's minimum window width (about 500px), not to the layout, and re-checked with Playwright's mobile viewport emulation: 0px horizontal overflow.

## 2. Reading the real task

**Prompt:** screenshots of the task email and API docs. *"please check this test task, what u think about it?"*

**What the AI found:**
- **A hard-rule conflict:** the bootstrap put the token in `EXPO_PUBLIC_API_TOKEN`, which gets inlined into the deployed bundle. The task forbids that, so the token became a runtime field kept in localStorage.
- It proposed answers for the three decisions (see `decisions.md`).
- It flagged that the scaffold commits are dated before the slot and suggested disclosing that in NOTES.md.

## 3. "Make it different from 100+ other candidates"

**Prompt 1:** *"we know that all users have similar tools and AI … let's think about what todo … to achive uniq result based on the task."*
→ The answer was a list of 7 possible features. It was useful, but generic.

**Prompt 2 (re-prompt):** *"what about if not only me get this … do analyze, check details and think in different way to achive this task"*
→ The AI probed the live API and decoded the token instead of listing features. Findings:
- The token payload contains `"chaos":"normal"`, so reviewers' tokens likely inject more failures.
- CORS only exposes `Retry-After` and `Idempotent-Replayed`, so the `Date` header can't be read and freshness has to come from `asOf`.
- ETH has 18 decimals (`12.345678901234591676`), which floats can't represent.
- The live API returns 2 destinations, while the docs example shows 1.
- 5xx/network failures on a POST are as "unknown" as a 504.

It proposed an architecture built on these findings:
- Balances derived by a pure `reconcile(snapshot, claims)`.
- An explicit claim state machine.
- A durable claim record.
- Client-side fault injection.

**Choice:** only the claim record + cross-tab lock was picked from the extras list (see `decisions.md`).

## 4. Money module

**Prompt:** *"use decmalsjs or big int"* → the AI recommended bigint (exact, no dependency, easy to explain).

**AI mistake caught:** its own test expected a USD total of `$32,035.12` and failed. Rather than "fixing" the code, the AI recomputed with Python `Decimal`, which gave `$32,035.30`, the same as the code. The test's expected value was wrong, so the test was corrected.

## 5. Build

The AI built, committing as it went:
- API client: `ApiError` split into rejected vs outcome-unknown, plus a client timeout.
- Token store, and `storage.ts` with Web Locks.
- Claim record state machine, journal and runner (send → unknown → replay with the same key → accepted → poll).
- `reconcile()`.
- Screens: token gate, Home, Claim (review/confirm), claim status, Activity.

Tests: 45 unit tests passed at this point. Typecheck and lint were clean, though stale typed-route files had to be regenerated by starting the dev server.

## 6. Verification ("run test mode to check if it was done")

The AI wrote a Playwright script (now `e2e/guards.mjs`) that drives the real API at 390px. Checks:
- Token gate, including a bad token.
- Validation for `.5`, `5`, too many decimals and too much, plus exact Max.
- Happy path.
- **Lost response:** the server got the POST but the browser saw a connection reset.
- Offline, then reload, then a second tab is blocked.
- Recovery after coming back online.
- The server's activity history has no duplicate claims.

**The first run had 20/21 passing.** The failing check asserted "exactly one POST", but the real API returned a **504** on an ordinary claim. The app showed "Confirming", replayed the same key, and got `200 Idempotent-Replayed`, with one claim. The test assumption was wrong, not the app. The check now asserts "same key and body for every attempt, at most one 201". **Second run: 21/21.**

Also checked:
- `dist/` and git history contain no token.
- The base URL appears in one file only.

## 7. Manual test by the user

The user ran the app and claimed Max USDT; it completed. A screenshot showed **"Completed"** next to **"Claiming 830.533207 USDT"**, because the snapshot predated the settlement. Fix: `reconcile()` now also removes claims that settled after the snapshot's `asOf` from claiming, and returns failed ones to available. A test was added: 46/46 pass.
